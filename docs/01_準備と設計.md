# 1. プロジェクトが始まる前にやること（準備と設計）

最初の打ち合わせ（キックオフ）から実際の作業が始まるまでに、チームの体制、進め方のルール、どんなものを作るかをお客様とすり合わせる準備セクションです。

## ディレクションシステムの考え方

- **段取りを一番大切にする** ― 作業を始める前に「誰が・何を・いつまでにやるか」を決めます。これだけで、現場で起きる行き違いや手戻りの多くを未然に防げます。
- **チーム内で言葉の定義を合わせる** ― 進み具合（ステータス）の書き方や判断基準をそろえます。全員が同じ意味で言葉を使うことで、意思疎通が格段にスムーズになります。
- **ミスが起きない仕組みを作る** ― 公開前の最終チェック（テスト）や承認の手順を最初から組み込んでおきます。確認もれによるミスを、個人の注意力だけに頼らず、仕組みで防ぎます。

## DiSAが定めるディレクションの原則

- ゴールと段取りを決める
- 周辺を巻き込んで合意形成する
- イニシアチブを握り続けて進捗する

## A-0. プロジェクトコンセプト（今回の優先順位をみんなで決める）

最初に「今回のプロジェクトでは何を最も大切にするか」をお客様と合意し、メンバー全員の判断軸をそろえます。

| 方針 | 中身 |
|---|---|
| スピード優先 | まずは最低限の機能で早く公開し、動きながら改善していく方針です。 |
| 品質優先 | 公開後のトラブルを防ぐため、事前の動作確認や表現の仕上がりを最も重視して完成度を高める方針です。 |
| コスト優先 | 決められた予算の範囲内で収めるため、まずは絶対に外せない機能だけを作り、残りは次のステップに回す方針です。 |
| 検証・学習優先 | 新しい技術やツールを試すことに価値を置き、チームのスキルアップやノウハウ獲得を重視する方針です。 |

書式: [templates/プロジェクトコンセプト合意.md](../templates/プロジェクトコンセプト合意.md)

## A-1. 制作プロセスと役割（ウォーターフォール／アジャイル）

進め方によって工程の区切りは変わります。最初に「誰が、どの工程を担うか」をはっきりさせて、役割の抜けや重複を防ぎます。

### ウォーターフォール

| 工程 | 中身 |
|---|---|
| 企画・プロデュース | 戦略設計／BS・PL（財務と損益の見通し）／数値目標（KGI・KPI） |
| 情報設計・仕様設計 | UX、IA、仕様設計／プロトタイピング、アートディレクション／システム、インフラ設計 |
| 制作・開発ディレクション | 要件定義・仕様書作成／進行管理（制作・開発）／QA（品質管理）・デバッグ |
| サービス運営・運用 | グロースハック、エンハンス／ABテスト→クリエイティブ→PDCA／システム運用・保守 |

### アジャイル

```
企画 → SPRINT 1（要件定義・設計・実装・テスト）→ リリース → SPRINT 2（要件定義・設計・実装・テスト）→ リリース
```

確認すること：今の自分はどの工程のディレクションができるか。次はどこへ広げるか。

## A-2. ディレクション初期設計（最初に決めておくべき7つのルール）

プロジェクトが動き出す前に、7つの分野それぞれで「どういう段取りで進めるか」を決めておきます。7つの分野は [ディレクション辞書](https://dic.drsp.cc/) の分類と同じです。はじめの4つはA-1の工程に対応し、残りの3つは全工程に共通します。

### A-1の工程に対応する4分野

#### 企画・プロデュース（方向性と体制）

「なぜこのプロジェクトをやるのか」という目的と財務・損益の見通し、役割分担（だれが何を決定するか）を決めます。

- 体制図（誰が決めるか）の作成
- 目標（何をもって成功とするか）の決定
- 財務と損益の見通し（BS・PL）の確認
- 連絡ツールと会議スケジュールの決定

辞書で詳しく：[Webサイト企画全般](https://dic.drsp.cc/dict/002/)

#### 情報設計・仕様設計（作るものの設計図）

画面の流れと情報の構造（UX・IA）、仕様、見た目の方向性、システムの構成を整理し、「思っていたのと違う」という作り直しを防ぎます。

- 画面遷移図・サイトマップの作成
- 仕様変更（やりたいことの変更）のルール設計
- プロトタイプとアートディレクション（見た目の方向性）の合意
- システム・インフラ構成とプログラムの命名規則の決定
- AI・LLMエージェント対応の設計（llms.txtの設置や構造化データの検討）

辞書で詳しく：[情報設計・仕様設計全般](https://dic.drsp.cc/dict/023/)

#### 制作・開発ディレクション（進行と品質の管理）

制作・開発・デバッグのそれぞれで、タスクが遅れていないか、品質が保たれているかを確かめながら進めます。

- 要件定義（何を作り、今回は何を作らないか）
- ステータス記号（`[ ]` `[/]` `[x]` `[!]`）による管理
- 古い仕様に戻ってしまうミス（先祖返り）の自動防止
- 公開前の動作確認（デバッグ）の手順と担当者
- 遅れ（`[!]`）が発生したときのリカバリー手順

辞書で詳しく：[制作・開発ディレクション全般](https://dic.drsp.cc/dict/041/)、[進行管理](https://dic.drsp.cc/dict/057/)

#### サービス運営・運用（公開後の改善と保守）

公開した後に、数字を見ながら改善を続ける仕組みと、データを安全に守る保守の手順を決めます。

- 改善の進め方（グロースハック・機能の追加）
- ABテストで効果を確かめ、PDCAを回すルール
- データ削除は「ゴミ箱マーク（論理削除）」を原則とする
- 定期的なデータ保存と復旧手順の確認
- ユーザーからの要望・改善点の集約ルール

辞書で詳しく：[サービス運営・運用全般](https://dic.drsp.cc/dict/078/)

### 全工程に共通する3分野

#### プロモーション（情報の届け方とSNS運用）

新しい機能のリリースやイベントのお知らせを、SNSなどを通じて効果的に世の中に発信します。

- SNSアカウントの運用ルールと責任者の決定
- リリース告知の文面レビュー・承認の流れ
- プレスリリース（公式発表）の確認ルート

辞書で詳しく：[プロモーション全般](https://dic.drsp.cc/dict/100/)

#### ライティング（言葉づかいと文章の一貫性）

サイト内のボタンの文字や説明文、操作説明書の言葉遣いを統一し、ユーザーが迷わないようにします。

- 画面上の言葉と説明書の一文字一句の一致
- 言葉の表記ゆれ（例：「お問い合わせ」と「お問合せ」）の防止
- 記事やコピーの確認・校正プロセス

辞書で詳しく：[ライティング全般](https://dic.drsp.cc/dict/113/)、[校正](https://dic.drsp.cc/dict/064/)

#### ツール・効率化（AIの活用と自動化）

AI（人工知能）を使って作業を早く終わらせる方法や、新しいメンバーがすぐにチームに慣れるマニュアルを作ります。

- AI向け指示書（AGENTS.md）の整備
- 繰り返しの作業を自動で終わらせる仕組みの導入
- 新メンバー用のオンボーディングマニュアルの用意

辞書で詳しく：[ツール・効率化全般](https://dic.drsp.cc/dict/119/)

## A-3. キックオフ合意テンプレート（打ち合わせでそのまま使えるメモ）

最初の打ち合わせ（キックオフ）で、お客様と必ず確認し合っておくべき14項目です。

1. プロジェクトコンセプト（スピードを優先するか、品質を優先するかなど）
2. 目的・成果指標（何をもってプロジェクトの成功とするか）
3. 作業範囲（やること / 今回はあえてやらないこと）
4. 役割分担（意見を出す人と、最終決定する1人 / 承認の流れ）
5. 連絡方法のルール（使うチャットツール / 定例会議の頻度 / 返信のルール / 議事録）
6. 緊急時の連絡ルート（どんな問題が起きたら、誰に、どう連絡するか）
7. 作業する場所とルール（ソースコードの管理 / 担当者のアクセス権限）
8. 使うツール、必要なアカウント、発生する費用（誰が負担するか）
9. デザインの設計図（design.md）を作るか（作る場合の担当者と更新ルール）
10. AI（人工知能）を使うルール（どの作業で使うか / 許可する範囲 / 禁止事項）
11. スケジュール管理（どうやって管理するか / 誰が更新するか / 大切な目標日）
12. 公開（リリース）の手順（手順 / 責任者 / トラブル時に元に戻す基準）
13. 作業完了の定義（これをもって完了とするお互いの合意）
14. 変更時のルール（やりたいことが途中で変わったときの相談・決定方法 / 決めたことを戻すときは、追加の見積もりと日程の相談になること）

辞書で詳しく：[キックオフ設計](https://dic.drsp.cc/dict/070/)
